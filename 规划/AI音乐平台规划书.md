## 1. 项目定位与愿景

### 1.1 一句话定位
为中国创作者提供一个**输入想法就能生成完整带人声歌曲**的 AI 音乐平台，体验对标 Suno，服务器位于香港，底层采用不受供应商内容政策约束的开源生成引擎（通过 API 调用）。

### 1.2 目标用户（中国客户为主）
- **个人音乐爱好者 / 短视频创作者**：需要 BGM、抖音 / 视频号配乐，不懂乐理也能出歌。
- **独立音乐人 / 词曲作者**：用 AI 快速做 demo、试听编曲方向。
- **企业 / 营销团队**：广告歌、品牌曲、活动主题曲，需可商用授权。
- **播客 / 知识付费主**：片头片尾曲、转场音效。

### 1.3 核心差异点（为什么是你）
| 差异点 | 说明 | 价值 |
|---|---|---|
| 香港服务器 | 面向大陆用户延迟低，且**无需大陆 ICP 备案**即可对外服务 | 上线快、合规路径灵活 |
| 无宗教限制引擎 | 调用开源模型的推理 API（或自托管），不被商业 API 的内容政策（宗教 / 题材 / 敏感词）卡脖子 | 创作自由度高，题材不受供应商限制 |
| 中文友好 | 选中文歌词 + 中文人声友好的模型组合 | 中国用户母语体验 |
| 免 GPU 租金 | API 优先，按需付费，MVP 零硬件投入 | 成本低、起步快 |
| Vibe Coding 构建 | 用 AI 编程从 0 到 1，成本低、迭代快 | 小团队 / 单人也能上线 |

### 1.4 成功标准（建议 KPI）
- MVP 上线后 3 个月：注册用户 ≥ 5,000，周活 ≥ 500，人均生成 ≥ 3 首。
- 生成一首 2–4 分钟带人声歌曲的端到端耗时 ≤ 90 秒（API 侧稳定时）。
- 用户生成内容（歌曲）过审率 ≥ 98%（自审 + 机审）。
- 6 个月内跑通订阅付费闭环，付费转化率 ≥ 3%。

## 2. 市场与竞争分析

### 2.1 市场背景
- AI 音乐进入"可用"阶段：从短片段（MusicGen 30s）发展到完整歌曲（YuE / DiffRhythm / Suno 2.0）。
- 中国短视频 + AIGC 内容需求爆发，BGM / 配乐是高频刚需。
- 国内同类（网易天音、腾讯琴乐、字节海绵音乐等）多为大厂内嵌，独立第三方平台仍有空间。

### 2.2 竞品对比
| 产品 | 引擎 | 中文体验 | 宗教/内容限制 | 服务器 | 对中国用户 |
|---|---|---|---|---|---|
| Suno | 自研（闭源） | 一般 | 有内容政策限制 | 海外 | 访问不稳定 |
| Udio | 自研（闭源） | 一般 | 有内容政策限制 | 海外 | 访问不稳定 |
| 国内大厂音乐 AI | 自研 | 好 | 严格（多重审核） | 大陆 | 合规但创作受限 |
| **本项目（API 优先）** | **开源模型推理 API** | **好（可定制）** | **无供应商限制** | **香港** | **低延迟免备案** |

### 2.3 机会点
1. **访问稳定性**：香港节点比美西/欧洲对中国用户更稳。
2. **题材自由度**：用开源模型（无论经 API 还是自托管）不被海外供应商的宗教 / 题材政策约束（即你强调的"无宗教限制"）。
3. **本土化**：歌词、曲风标签、支付方式（微信 / 支付宝 / 香港钱包）、社区语言全中文化。
4. **商用授权清晰**：独立平台可提供明确的可商用 license，区别于"大厂免费但归属不清"。
5. **低成本起步**：API 优先免去 GPU 硬件投入，MVP 现金流压力小。

## 3. 核心产品功能规划（对标 Suno）

### 3.1 创作核心（最重要的页面）
- **自定义模式（Custom Mode）**
  - 输入**风格标签**（如：国风、说唱、Lo-fi、K-pop、古风、电子）。
  - 输入**主题 / 情绪**（如："失恋的雨夜，伤感，钢琴"）。
  - 可**粘贴自定义歌词**（或让 AI 生成）。
  - 可选**人声性别 / 音色预设**。
- **智能模式（Simple Mode）**
  - 一句话描述 → AI 自动拆成风格 + 歌词 + 结构并生成。
- **歌曲结构控制**：主歌 / 副歌 / 桥段 / 前奏 / 尾奏（靠引擎能力或分轨拼接实现）。
- **歌词生成器**：基于开源/云端 LLM 生成中文歌词（带韵脚、带结构标注）。
- **参考音频 / 风格迁移**（进阶）：上传一段旋律或参考，做风格续写（看引擎支持）。

### 3.2 听感与编辑
- **在线播放器**：波形图、进度、循环、下载。
- **分轨导出**（进阶）：人声 / 伴奏分离，方便二次创作。
- **变体生成（Remix / 续写）**：同一 prompt 生成 2–4 个版本让用户挑。
- **基础编辑**（MVP 后）：裁剪、淡入淡出、调音量（用 ffmpeg / 前端音频库）。

### 3.3 探索与社区
- **发现页（Explore）**：热门歌曲流、按风格筛选、排行榜。
- **个人主页 / 作品库**：我的生成历史、收藏、公开 / 私密设置。
- **分享**：生成卡片图（带封面 + 歌名 + 二维码），便于抖音 / 朋友圈传播。

### 3.4 账户与订阅
- 邮箱 / 手机 / 第三方（微信）登录。
- **积分 / 订阅**体系（详见第 10 章）。
- 商用授权管理：标记"可商用"版本，提供授权证书下载。

### 3.5 管理后台
- 内容审核台（机审 + 人工复核）。
- 生成任务状态监控（API 调用量、队列长度、失败率）。
- 用户 / 订单 / 财务看板。
- 风格标签库管理。

## 4. 技术架构总览

### 4.1 总体分层
```
┌─────────────────────────────────────────────┐
│  客户端层（Web / 移动 H5）                    │
│  Next.js + Tailwind + 播放器组件             │
└───────────────┬─────────────────────────────┘
                │ HTTPS / WSS
┌───────────────▼─────────────────────────────┐
│  API 网关 / BFF（Node.js / Next API Routes） │
│  鉴权 · 限流 · 任务提交 · 文件代理            │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│  业务服务层（Python FastAPI）                 │
│  用户 · 订单 · 作品 · 审核 · 内容策略          │
└───┬───────────────┬───────────────┬─────────┘
    │               │               │
┌───▼───┐   ┌───────▼───────┐   ┌───▼──────────┐
│ 队列   │   │ 生成编排服务   │   │ 存储 / CDN    │
│Redis/  │   │ (调用推理 API  │   │ 对象存储 +    │
│Celery/ │   │  + 后处理)     │   │ 香港 CDN      │
│队列    │   │                │   │               │
└───────┘   └───────────────┘   └──────────────┘
                │
┌───────────────▼─────────────────────────────┐
│  数据层                                       │
│  PostgreSQL（业务）· Redis（缓存/队列）        │
└─────────────────────────────────────────────┘
                │
        ┌───────▼───────────────┐
        │  推理 API 市场          │
        │ (Replicate/Fal + 开源   │
        │  模型 YuE/CosyVoice…)  │
        └────────────────────────┘
```

> **v1.1 架构要点**：生成算力**不落在你自己的 GPU 上**，而是由"生成编排服务"调用外部推理 API（Replicate / Fal.ai 等）完成。你只需付 API 调用费，无需采购/运维 GPU 服务器。详见第 5 章。

### 4.2 前端技术栈（Vibe Coding 友好）
- **框架**：Next.js（App Router）+ React + TypeScript。
- **样式**：Tailwind CSS（AI 生成 UI 最友好）。
- **播放器**：wavesurfer.js（波形）+ Howler.js（播放控制）。
- **状态**：Zustand（轻量，AI 易写）。
- **组件库**：shadcn/ui（可复制源码，Vibe Coding 神器）。
- **部署**：Vercel 或香港静态托管（前端可走 CDN）。

### 4.3 后端技术栈
- **业务 API**：Python FastAPI（与 AI 生态一致，便于 Vibe Coding 共用上下文）。
- **任务编排**：生成编排服务统一封装各推理 API（歌词 LLM、音乐模型、人声模型、后处理），对上游提供统一接口。
- **任务队列**：Celery + Redis / 轻量队列，用于 API 异步调用与状态回写（避免用户长等待）。
- **鉴权**：JWT + Refresh Token；第三方登录用 Authlib（微信 / 邮箱）。
- **支付**：微信支付（跨境/香港商户）、支付宝（香港）、Stripe（海外卡）三选做。
- **对象存储**：香港区对象存储（如腾讯云香港 COS / AWS ap-east-1 / 自建 MinIO）。
- **CDN**：香港 / 亚太节点加速音频分发。

### 4.4 音频生成管线（核心，API 化）
```
用户输入(prompt+歌词)
   ↓
[歌词 LLM API] 生成/润色带结构标注的中文歌词   (若用自定义歌词则跳过)
   ↓
[音乐生成 API] 生成伴奏/旋律 (YuE/DiffRhythm… 经 Replicate/Fal)
   ↓
[人声合成 API] 用歌词+旋律合成人声 (CosyVoice/RVC 经推理 API)
   ↓
[对齐与混音] 人声+伴奏对齐、混音、母带 (服务端轻量 ffmpeg/librosa)
   ↓
[审核] 歌词/音频机审 → 入库 + CDN
   ↓
返回播放/下载链接
```
> 重算力全部在外部推理 API，你的服务只做**编排 + 轻量后处理 + 审核 + 存储**，服务器负载极低。

### 4.5 推理与调用（API 优先，免 GPU）
- **调用方式**：通过推理 API 市场（Replicate / Fal.ai 等）调用开源模型，按调用量 / 时长计费，**不采购 GPU**。
- **并发与排队**：API 有速率/并发上限，用队列削峰；免费用户排队，付费用户优先/更高配额。
- **容错**：多供应商备份（如 A 模型在 Replicate，B 在 Fal），单点故障可切换。
- **兜底（可选）**：若后期 API 成本过高或对管控有要求，再切到路线 C 自托管（见 5.1、5.4）。

### 4.6 存储与 CDN
- 音频文件（mp3/wav）存对象存储，元数据存 PostgreSQL。
- 播放走 CDN，降低回源与延迟。
- 生成中的临时文件定时清理，控制成本。

### 4.7 数据库
- PostgreSQL：用户、订单、作品、标签、审核记录。
- Redis：队列、限流、热点缓存（热门歌曲、用户 session）。
- （可选）向量库：做"相似歌曲推荐 / 以歌搜歌"。

## 5. 音乐生成引擎深度选型（重点：无宗教限制）

### 5.1 架构路线更新（API 优先 · 免 GPU 租金）

你提出：调用国际版 API 即可，无需自租 GPU。这能显著降低 MVP 成本与上线门槛，本规划据此将**API 优先**调整为主线。但需先澄清一个事实，避免后续踩坑：

> **事实澄清**：国际商业音乐 API（如 Suno API、Udio 等）**并非"完全无限制"**——它们都有各自的服务条款与内容审核策略（仇恨言论、儿童安全、部分宗教 / 政治题材等仍会被拦截）。你最初强调的"无宗教限制"诉求，纯商业 API 不一定能满足。
>
> **真正两全的路径**：用**推理 API 市场（Replicate / Fal.ai / 类似平台）运行开源模型（YuE、MusicGen、DiffRhythm 等）**。好处：① 不租 GPU、按需付费（满足"没必要租 GPU"）；② 底层是开源权重，**模型本身无供应商内容政策**（满足"无宗教限制"）；③ 有 API 便利、易集成。

#### 三条子路线对比
| 路线 | 是否租 GPU | 内容限制来源 | 成本结构 | 适合阶段 |
|---|---|---|---|---|
| **A. 商业 API**（Suno/Udio 等） | 否 | 厂商内容政策（仍有） | 按量/订阅，无硬件 | 极速验证；但题材受厂商约束 |
| **B. 推理 API 跑开源模型**（Replicate/Fal + YuE 等）⭐推荐 | 否 | 无（开源权重） | 按量 GPU 费，无硬件 | MVP→成长：免 GPU 且真正无宗教限制 |
| **C. 完全自托管**（原方案） | 是 | 无 | 硬件+运维重 | 规模做大 / 要完全自主掌控时 |

**推荐主线**：MVP 走 **路线 B**——Replicate/Fal 跑 YuE（伴奏）+ CosyVoice/RVC（人声）+ 云端或自托管 LLM（歌词）。既免 GPU，又保住"无宗教限制"。
**路线 A** 仅作"接受厂商限制前提下"的极速验证备选。
**路线 C** 作为后期规模化、或要对生成管线做深度定制 / 合规自主时的可选升级（届时再参考 5.4 的部署参数）。

> 注意区分两层：
> - **引擎层（生成模型）**：路线 B 用开源权重 → 实现"无宗教限制"；路线 A 用商业 API → 受厂商政策约束。
> - **平台运营层（面向中国客户）**：无论哪条路线，都仍需做合规审核（见第 7 章），这是法律要求，不是引擎限制。两者不矛盾。

### 5.2 候选开源模型对比（经推理 API 调用）

#### A. 音乐 / 伴奏生成
| 模型 | 开源 | 特点 | 中文/长歌曲 | Replicate/Fal 可部署 | 推荐度 |
|---|---|---|---|---|---|
| **YuE**（m-a-p + 网易） | 是 | 支持多语言歌词、长序列、旋律续写，中文友好 | 强 | 是 | ⭐⭐⭐⭐⭐ 首选 |
| **DiffRhythm** | 是 | 最近开源，支持几分钟完整歌曲生成 | 较强 | 是（社区镜像） | ⭐⭐⭐⭐ 备选 |
| **MusicGen / AudioCraft**（Meta） | 是 | 成熟稳定，30s 片段，文/旋律到音乐 | 一般（无歌词） | 是 | ⭐⭐⭐ 基础 |
| **Stable Audio**（Stability） | 是 | 可生成较长音频，音质好 | 一般 | 是 | ⭐⭐⭐ 备选 |
| **ACE-Step** | 是 | 开源音乐生成，社区活跃 | 中 | 是（社区镜像） | ⭐⭐⭐⭐ 备选 |

#### B. 人声 / 歌声合成
| 模型 | 开源 | 特点 | 中文 | Replicate/Fal 可部署 | 推荐度 |
|---|---|---|---|---|---|
| **CosyVoice**（阿里） | 是 | 多语言 TTS，中文强，可克隆音色 | 强 | 是（社区镜像） | ⭐⭐⭐⭐⭐ 首选 |
| **RVC**（Retrieval VC） | 是 | 高质量声音转换，社区模型多 | 强 | 是 | ⭐⭐⭐⭐ 人声转换 |
| **So-VITS-SVC** | 是 | 歌声合成经典方案 | 强 | 是 | ⭐⭐⭐⭐ 备选 |
| **OpenVoice** | 是 | 音色克隆轻量 | 中 | 是 | ⭐⭐⭐ 备选 |

#### C. 歌词 LLM（云端 API 或自托管，避免内容政策）
| 模型 | 开源 | 中文 | 推荐度 |
|---|---|---|---|
| **Qwen（通义千问）系列** | 是 | 强 | ⭐⭐⭐⭐⭐ |
| **DeepSeek 系列** | 是 | 强 | ⭐⭐⭐⭐⭐ |
| **Llama 中文微调** | 是 | 中 | ⭐⭐⭐ |

> 歌词 LLM 可用云端 API（Qwen/DeepSeek 开放平台）即可，成本极低；若担心内容政策，也可经推理 API 自托管开源权重版本。

### 5.3 推荐组合（API 优先版）
- **歌词**：云端 Qwen / DeepSeek API（中文歌词 + 结构标注），或自托管开源权重。
- **伴奏/旋律**：**YuE**（经 Replicate/Fal）为主；**DiffRhythm** 作备选扩展。
- **人声**：**CosyVoice**（经推理 API）或 **RVC**（音色克隆）。
- **后处理**：Demucs（分轨，可 API 或轻量服务端）、ffmpeg / pyloudnorm（混音母带，服务端轻量执行）。

> 这套组合**全部走 API 调用开源权重**，没有任何供应商内容政策 → 完全符合"无宗教限制"诉求，且中文体验最佳，同时**无需你自租 GPU**。

### 5.4 部署参数参考（仅路线 C 自托管时适用）
> 以下参数仅在你后续切换到**路线 C（完全自托管）**时才需要；路线 B（API 优先）无需采购硬件。

- 起步 GPU：1× RTX 4090 / 5090（24–32G 显存）可跑量化后的 YuE + CosyVoice。
- 生产：2–4× 80G 级 GPU（A100/H100 或 5090×多卡）做并发 Worker。
- 推理服务：用 vLLM / 各模型官方推理脚本封装成 gRPC/HTTP Worker。

## 6. 香港服务器与基础设施规划

### 6.1 为什么选香港
- **低延迟到大陆**：RTT 通常 20–60ms，比美西/欧洲快很多。
- **免 ICP 备案**：香港服务器对中国大陆用户开放访问无需工信部备案，上线快。
- **国际带宽**：出海中转方便，未来可加东南亚节点。
- **法律环境**：数据合规路径比纯大陆灵活，但仍需遵守中国相关法律（见第 7 章）。

### 6.2 服务器选型
| 层 | 选型 | 说明 |
|---|---|---|
| 前端 / API / 编排服务 | 香港轻量云 / 容器 | 2–4 核即可，无重负载（重算力在外部 API） |
| GPU 推理 | **路线 B 无需**；仅路线 C 才需香港 GPU 云或自建机柜 | API 优先时本项为零成本 |
| 数据库 / 存储 | 香港区对象存储 + 云数据库 | 备份到异地 |
| CDN | 亚太节点 | 加速音频，降低回源 |

### 6.3 域名与网络
- 域名：建议 `.com` / `.ai` 国际域名（避免 `.cn` 强制备案联动）。
- DNS：Cloudflare（香港/亚太节点，顺带做基础防护与缓存）。
- HTTPS：Let's Encrypt 或 Cloudflare 证书。

### 6.4 成本提示（API 优先）
- **最大成本项从"GPU 硬件"变为"推理 API 调用费 + 存储/CDN 流量"**，按需付费、无固定硬件投入。
- 用队列削峰 + 免费层限额，控制 API 调用总量。
- 监控单首歌的推理成本，设置付费墙/积分抵扣，避免"免费用户把 API 额度薅穿"。

## 7. 合规与风控（面向中国客户）

> 关键认知：**"无宗教限制引擎"指的是生成模型不受供应商内容政策约束；但作为面向中国用户的平台，运营侧仍需依法做内容合规。** 这两层要分清楚，否则有法律风险。

### 7.1 内容审核（必须）
- **歌词机审**：自托管敏感词库 + 分类模型，生成前先审歌词文本。
- **音频机审**：语音识别（ASR）转文字后再审 + 音频特征风控。
- **人工复核**：机审存疑进人工台（第 3.5 章后台）。
- 目标：过审率 ≥ 98%，违规内容不出库。

### 7.2 版权与授权
- 明确平台生成内容的**版权归属与商用授权条款**（用户协议写清）。
- 引擎若用开源模型，注意各自 **License**（如 MIT / Apache / 社区非商用条款），商用前确认合规。
- 不为用户生成"模仿特定真人歌手音色"提供现成能力（避免肖像/声音权纠纷）——音色克隆限用户自有/授权素材。

### 7.3 数据合规
- 遵守《个人信息保护法》（PIPL）：明示收集、最小化、可删除。
- 大陆用户数据跨境：香港属境外，需做跨境传输合规说明（隐私政策 + 用户同意）。
- 日志 / 内容留存满足监管要求周期。

### 7.4 支付合规
- 微信 / 支付宝：走香港商户或合规跨境方案。
- 保留订单、退款、发票能力。
- 避免虚拟货币等灰色支付。

### 7.5 宗教 / 政治内容
- 引擎层"无宗教限制"≠ 平台可放任违规宗教/政治内容。
- 平台侧用审核词库 + 策略兜底，确保不触碰中国法律红线。
- 这恰恰是用开源模型（路线 B）的优势：**你自己掌控审核粒度**，而不是被海外供应商一刀切。

## 8. Vibe Coding 开发工作流（全项目用）

### 8.1 什么是本项目的 Vibe Coding
> 用自然语言描述需求，由 AI 编程工具（Cursor / Claude / Trae / 通义灵码 等）生成并迭代代码，**你做架构决策 + 验收，AI 做实现**。整个前端、后端、编排服务、调用封装、部署脚本都用这套方式推进。

### 8.2 推荐工具链
| 用途 | 工具 | 备注 |
|---|---|---|
| 主力 IDE | Cursor（或 Trae / VS Code + Copilot） | 多文件上下文、Agent 模式 |
| 前端生成 | shadcn/ui + Tailwind（复制即用的组件） | 降低 AI 出错 |
| 后端生成 | FastAPI + Pydantic 脚手架 | AI 写 API 很稳 |
| 提示词/SOP | 每个模块一个 `PROMPT.md` | 记录"怎么让 AI 写这个模块" |
| 版本 | Git + 频繁小提交 | 出错了好回滚 |
| 预览 | 本地 + Vercel 预览 | 快速看效果 |

### 8.3 模块拆分与 AI 协作建议
把项目拆成**小而独立、AI 可一次写对**的模块，逐个 Vibe 出来：
1. `frontend/`：页面、播放器、创作表单（Next.js）。
2. `backend/`：FastAPI 用户/订单/作品 CRUD。
3. `auth/`：登录、JWT、第三方。
4. `engine/`（v1.1 改名 `orchestrator/`）：**生成编排服务**——统一封装各推理 API（歌词 LLM、YuE、CosyVoice/RVC、后处理）。
5. `queue/`：Celery/Redis 任务提交与状态轮询。
6. `storage/`：对象存储上传/下载/CDN。
7. `admin/`：审核台、监控。
8. `deploy/`：Docker / docker-compose / 香港服务器脚本（不含 GPU 训练）。

### 8.4 提示词工程 SOP（示例模板）
```
你是一个资深 {前端/后端/ML} 工程师。请在 {目录} 实现一个 {功能}，
技术栈：{Next.js 14 + TS / FastAPI + Pydantic}。
要求：
1. 输入/输出契约（JSON 字段）见 {schema}。
2. 错误处理用 {统一格式}。
3. 注释用中文，函数单一职责。
4. 不要改写无关文件。
5. 写完后给出自测命令。
```
> 把每个模块的契约（字段、接口、错误码）先定清楚，再让 AI 写，质量高很多。

### 8.5 质量保障（Vibe 不等于裸奔）
- **契约先行**：先定义 API/数据 schema，再生成实现。
- **小步提交**：AI 每改一个模块就 commit，方便 diff/回滚。
- **人工验收**：你跑起来看效果 + 读关键代码，不盲信。
- **测试**：核心链路（提交→API 生成→审核→入库）写最小 smoke test。
- **代码评审习惯**：让 AI 自己 explain / review 一遍再合。
- **API 调用封装**：所有外部推理 API 调用集中在一个 `orchestrator/providers/`，便于换供应商与限流。

## 14. 多端同步与 APK 集成（同步到 FLOW APP）

### 14.1 需求拆解（先对齐前提，避免幻觉）
用户诉求：「制作完的音乐，点一下『同步到 FLOW APP 的音乐单』，后台把这首歌同步过去，FLOW APP 里就能看到/播放。」
要把这件事规划清楚，必须先确认两个前提，否则架构无法定、容易写成幻觉：

- **前提 A：FLOW APP 是谁的？**
  - 情况 1（推荐、最自洽）：FLOW APP 是你**自己的 Android 应用**，且你有它的后端（或它直接复用本平台后端）。这样你能定义同步接口，实现真正的「后台推送/拉取同步」。
  - 情况 2：FLOW APP 是**第三方 App**。第三方消费类音乐 App 通常不对外暴露「添加我的歌单」的写入 API，你的后台**无法直接写入**其歌单。可行做法只有用户手动分享（Android 系统分享 Intent）或深度链接，那不是「后台自动同步」。
- **前提 B：音频在网络上是否可达？** Suno 返回的 `audioUrl` **可能**是临时/会过期的，且对大陆访问不一定稳定。要做到 APK 稳定播放，平台应先把音频**回源到香港 CDN**（见 4.6 / storage 模块），同步 CDN 链接而非原始链接。

> ⚠️ 本章默认 **前提 A = 情况 1（FLOW APP 为你自有应用）** 展开；若为情况 2，见 14.7。所有 `/flow/...` 接口名仅为示意，真实字段以你 FLOW 后端实现为准，**不假设任何第三方 App 有此接口**。

### 14.2 推荐架构（自有 APK + 自有/共享后端）
```
[Web 平台]                        [FLOW 后端 / 或平台后端]              [Android APK]
创作页「同步到 FLOW」按钮
   │  POST /api/songs/{id}/sync-flow
   ▼
[平台后端]
   ├─ 校验：歌曲归属 + 已过审 + 账号已绑定
   ├─ 确保音频已回源 CDN（storage.upload_bytes）
   └─ 写 SyncRecord(status=pending)
        │  (Push 模式) POST /flow/api/v1/playlist/add
        ▼
   [FLOW 后端] 写入该用户歌单 ──(Pull 模式则跳过，APK 自行拉取)──┐
                                                                    │
[Android APK] 打开/刷新 → GET /api/sync/flow(或 /flow/api/v1/playlist)◄┘
        ← 拉取歌单（CDN 音频链接、封面、歌词）
        → ExoPlayer/Media3 播放；Room 本地缓存
```
两种同步模式（二选一或并存）：
- **Pull（拉取，推荐 MVP 先用）**：APK 打开时带用户 token 调用 `GET /api/sync/flow`，拿到歌单，本地存 Room。Web 点「同步」只是把歌曲标记为可同步（或触发一次 CDN 回源）。优点：只需平台后端一家、最稳。
- **Push（推送）**：Web 点「同步」→ 平台后端调用 FLOW 后端 `POST /flow/api/v1/playlist/add`，主动写入。优点：实时；缺点：要求 FLOW 后端暴露该接口且账号打通。

### 14.3 同步接口契约（REST，真实可行，无虚构字段）
平台侧新增（挂在现有 FastAPI）：
- `POST /api/songs/{song_id}/sync-flow`
  - 鉴权：Bearer（同现有）
  - 前置：`status==completed` 且已过审；用户已绑定 FLOW 账号
  - 行为：确保音频回源 CDN → 写 `SyncRecord` →（Push 模式）调用 FLOW 后端
  - 返回：`{ "sync_id", "status": "synced|pending|failed", "audio_cdn_url" }`
- `GET /api/sync/flow?since=<ts>`（Pull 模式供 APK 拉取）
  - 返回该用户歌单：`[{song_id,title,audio_cdn_url,cover_url,lyric,duration,style,synced_at}]`
- `GET /api/songs/{id}/sync-flow` 查询单条同步状态。

FLOW 后端侧（仅 Push 模式需要，由你定义，示例）：
- `POST /flow/api/v1/playlist/add` body `{user_token, song:{id,title,audio_cdn_url,cover_url,lyric}}` → 200 写歌单。
> 注：`/flow/...` 为示意命名，真实字段以你 FLOW 后端实现为准；不假设第三方 App 有此接口。

### 14.4 账号绑定（关键，避免「同步到别人歌单」）
- 若 FLOW APP 复用平台鉴权（同一 JWT/用户体系）：APK 登录即绑定，最省事。
- 若 FLOW 有独立账号：做「绑定」流程——用户在 FLOW APP 内用平台账号授权，或输入绑定码；平台存 `user.flow_token`。同步时携带该 token 调 FLOW 接口。
- 务必校验：被同步的歌曲只能进**当前登录用户**的歌单（平台侧用 `song.user_id` 校验归属）。

### 14.5 音频可达性（最容易翻车的点）
- Suno 原始 `audioUrl` **不稳定，不要直接同步原始链接**。
- 流程：平台 `storage.upload_bytes(key, 下载的音频bytes)` → 得到香港 CDN 公共链接 → 同步该 CDN 链接。
- 好处：大陆 APK 播放稳定、链接不过期。storage 模块（`backend/app/storage/s3.py`）已为此预留。

### 14.6 UI 流程与状态机（UI ↔ Process ↔ Function 对齐）
Web 端（歌曲卡片上的「同步到 FLOW」按钮）：

| UI 状态 | 触发 | 后端 Process | 对应函数/模块 | 数据变化 |
|---|---|---|---|---|
| 按钮可点 | 歌曲 completed | — | — | — |
| 「同步中…」(spinner) | 点击 | 校验 + 回源 CDN + 写 SyncRecord + 调 FLOW | `songs.sync_flow` / `storage` / `orchestrator` | `SyncRecord.status=pending` |
| 「已同步」✓ | 后端成功 | 写入歌单 | FLOW 后端 `playlist/add` | `SyncRecord.status=synced` |
| 「失败·重试」 | 异常/超时 | 记录失败 | 异常捕获 | `SyncRecord.status=failed` |
| 禁用（灰） | 未完成/未过审 | 拒绝 | 前置校验 | 返回 400/409 |

APK 端（FLOW APP 音乐单）：

| UI 状态 | 触发 | 后端 Process | 函数/模块 | 数据 |
|---|---|---|---|---|
| 空歌单 | 首次打开 | 拉取 `GET /api/sync/flow` | Retrofit call | Room 空 |
| 列表项(封面+标题+时长) | 拉取成功 | 解析列表 | JSON→Room | 歌单数据 |
| 播放中 | 点击某项 | 取 audio_cdn_url | ExoPlayer/Media3 | 播放进度 |
| 同步失败提示 | 拉取/播放异常 | 错误 | try/catch | toast |

### 14.7 若 FLOW APP 是第三方（诚实说明）
- **无法由你的后台直接写入其歌单**（第三方一般无开放写入 API）。
- 可行替代：
  1. 用户点「分享到 FLOW」→ Android `Intent.ACTION_SEND` 把音频文件/链接发送过去（**每次手动**，非后台自动）。
  2. 若 FLOW 支持**深度链接 / URL Scheme**：生成 `flow://add?...` 让用户跳转添加。
  3. 真正「后台自动同步」必须你**控制 APK**（自建 FLOW APP 或拿到其 API 合作）。
- 结论：你描述的「后台会同步音乐过去」只有在 FLOW APP 受你控制时才成立。请确认前提 A。

### 14.8 APK 端实现要点（真实组件，非虚构）
- 网络：Retrofit2 + OkHttp（调同步接口）、Coil/Glide（封面）。
- 存储：Room（本地歌单缓存，离线可见）。
- 播放：AndroidX Media3 ExoPlayer（流式播放 CDN 音频）。
- 同步触发：App 启动 + 下拉刷新 + 可选 FCM 推送「有新歌已同步」。
- 账号：与平台共用登录态（JWT 存 DataStore）。
- 这部分通常是**独立仓库/独立构建**（Android Studio / Gradle），不在本 Next.js+FastAPI 仓库内；通过同一套 REST 契约对接。

### 14.9 待你确认（不拍脑袋）
1. FLOW APP 是你**自有应用**（有后端/可改）还是**第三方**？（决定 14.2 / 14.7 走哪条）
2. 同步用 **Pull** 还是 **Push**（建议 MVP 先 Pull）？
3. FLOW APP 是否复用平台账号体系？
4. APK 是否由你这边开发？技术栈（原生 Kotlin / Flutter / React Native）？

## 14.10 已确认决策（2026-08-26）
- FLOW APP = **自有应用**；APK 由本人开发（独立工程，不在本仓库）。
- **账号复用**：FLOW APP 使用同一平台 JWT，无需独立绑定流程。
- **同步模式**：MVP 采用 **Pull**——平台后端负责音频回源香港 CDN + 打同步标记（`SyncRecord`），APK 用同一 JWT 调 `GET /api/sync/flow` 拉取自己的歌单。后续若 FLOW 有独立后端且要实时，可加 Push 到 `/flow/api/v1/playlist/add`。
- **范围**：该功能先开发，后续公开使用；已内置鉴权、归属校验、限流位（待加），满足公开前的安全要求。
- 后端接口已实现：`POST /api/songs/{id}/sync-flow`、`GET /api/sync/flow`、`GET /api/songs/{id}/sync-flow`；APK 对接契约见仓库根 `FLOW_APP_API.md`。

| UI 控件 | Process（后端流程） | Function / 接口 | 代码位置 |
